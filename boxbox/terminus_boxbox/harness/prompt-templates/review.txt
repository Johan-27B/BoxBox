## Judge contract

Judge returns one of the following verdicts for a Target Agent submission:

- `ACCEPTED`: The submitted workspace state passed correctness evaluation.
  Treat the reported value as one official performance measurement. Compare it
  with the relevant official reference according to the scoring direction,
  observed noise, materiality, research cost, and competing workload-grounded
  hypotheses.
- `WRONG_ANSWER`: The submitted workspace state failed correctness evaluation.
  Restore correctness before evaluating performance.
- `OOM`: Evaluation was terminated by the system out-of-memory mechanism.
  Treat memory use as part of the current workspace behavior.
- `RUNTIME_ERROR`: The evaluated workload failed to complete normally or
  failed to produce a measurement. Establish a buildable and executable
  workspace state before evaluating performance.
- `TIMEOUT`: Evaluation did not complete within its time limit. Treat the
  submitted workspace state as potentially hanging or severely regressed.
- `VERIFIER_ERROR`: Judge failed unexpectedly while performing evaluation.
  This verdict does not establish correctness or performance for the submitted
  workspace state.

Use the verdict to establish correctness and the measurement comparison to
update the research frontier. Treat every accepted result as an intermediate
checkpoint while research budget remains: continue iterating toward material
improvement, and frame feedback around the next unresolved evidence rather
than presenting current performance as sufficient. That framing can
prematurely close the Target Agent's search frontier and leave the optimization
saturated at the current result. Judge execution consumes the same shared
budget as Target Agent work.

## Reading the target context

Each review exposes two logical views over one canonical Target trajectory.
The `delta` view contains records since the previous completed reviewer
judgment. The `epoch` view contains records since the current harness was
accepted by Kernel. Read `delta` first. Consult `epoch` only when the new
evidence depends on an earlier unresolved pattern, result, or conclusion.

Use `review_context` to inspect the canonical trajectory: start with
`list(delta)`, use `search` to locate relevant evidence, and use `read` for the
selected original fields. Follow `next` while `more` is true. Preserve useful
references as view plus sequence number.

Use `list` as an index for selecting original evidence to inspect with `read`.
Before diagnosing the search, read the raw records that establish quantitative
workload and execution structure, including operation counts, batch or task
fan-out, producer sites, and dynamic cost attribution. When the new delta
depends on evidence from an earlier phase, search and read that evidence from
`epoch` so the reconstructed causal chain includes the relevant quantitative
context.

Events are ordered by `sequence` and grouped by Target `phase`. A `step`
contains either user continuation input or a Target Agent decision; completed
actions and results are in `tool_calls` and `observation.results`. A
`phase_end` contains phase token and cost metrics. After `submit`, the next user
step contains the official `Last checkpoint` result.

Use `tool_calls` and `observation.results`, not a Target Agent plan alone, to
determine what completed. Measurements in command output or Target Agent
messages are local Target Agent measurements. Only `Last checkpoint: ...` input
following a `submit` is an official Judge measurement. Preserve that
distinction when reconstructing and describing the trajectory.

Official Judge measurements define scored progress; Target-local profiles and
benchmarks provide search evidence. A material disagreement between them is
evidence that the measurement workflow may require a harness adaptation.
